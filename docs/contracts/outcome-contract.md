# Outcome contract

**What marks a group of calls a task, and what "succeeded" means precisely enough to divide by.**
[ADR-0003](../adr/0003-cost-per-outcome.md) decided the denominator is successful outcomes, not
calls or tokens; this document is the contract that makes "successful outcome" a fact a system can
record rather than an opinion a dashboard asserts.

## The outcome record

A task — one or more correlated calls working toward one unit of product-visible work — has
exactly one outcome record:

| Field | Type | Notes |
| --- | --- | --- |
| `outcome_id` | string | The same value every one of the task's cost events carries. Generated by whatever code starts the task (a request handler, an agent loop's entry point), before the first call. |
| `feature`, `tenant` | string | Copied from the task's context; must match the `feature`/`tenant` on every cost event sharing this `outcome_id` — a mismatch is a propagation bug, not a valid state. |
| `status` | enum: `pending`, `succeeded`, `failed`, `abandoned` | See below. |
| `opened_at` | RFC 3339 | When the first call for this task was made. |
| `resolved_at` | RFC 3339, nullable | When `status` left `pending`. Null while `pending`. |

## The states

- **`pending`** — the task has made at least one call and has not yet resolved. This is the
  starting and default state, per the sequence in
  [instrumentation.md](../diagrams/instrumentation.md#from-a-call-to-an-alertable-regression):
  "cost event, tagged, outcome pending."
- **`succeeded`** — the task's owner (see below) explicitly marked it done and its result
  acceptable. This is the only status that counts toward the denominator in cost per outcome.
- **`failed`** — the task's owner explicitly marked it done and its result unacceptable, or a call
  returned a terminal error the task's own retry policy chose not to retry. Contributes its cost to
  the numerator, nothing to the denominator — this is precisely how [ADR-0003](../adr/0003-cost-per-outcome.md)
  makes waste visible.
- **`abandoned`** — the task never reached `succeeded` or `failed` within its resolution window
  (see below) and is not still legitimately in flight. This is the "abandoned work" row in
  [cost-model.md](../cost-model.md)'s waste table: tokens spent on a task nobody finished. Counted
  with `failed` for the cost-per-outcome denominator (contributes cost, not a successful outcome) —
  a resolution status distinct from `failed` mainly for diagnosis: "we lost track of it" is a
  different bug than "it explicitly errored."

**No fifth state, deliberately.** [ADR-0003](../adr/0003-cost-per-outcome.md)'s negative
consequences name "partial success" as a real source of dispute. This contract's answer: a task
that produced a partial or degraded result is not a new state — its owner decides, at resolution
time, whether that result counts as `succeeded` or `failed` for this feature's purposes, using
whatever product-specific bar applies. The *contract* only has room for a binary answer at
resolution; where the line sits is the feature's business logic, documented at the call site, not
this schema's problem to model.

## Who resolves an outcome, and when

**The task's owner — the code that knows what the task was trying to do — resolves it exactly
once, explicitly.** Not the instrumentation boundary: the boundary sees calls, not tasks, and has
no way to know whether a task's result was acceptable
([ADR-0004](../adr/0004-instrument-at-the-boundary.md)'s boundary is deliberately business-logic-blind).

- Resolution is a single write from `pending` to `succeeded` or `failed`. A resolved outcome is
  immutable — a task does not un-succeed.
- **Every task must define a resolution window** — the maximum time after `opened_at` it may stay
  `pending` before something (a sweep job, a timeout in the task's own framework) moves it to
  `abandoned`. A task with no resolution window is a cost-observability leak: its cost sits in
  `pending` forever, invisible to both the numerator and the denominator, understating cost per
  outcome indefinitely. Milestone 3's reference implementation ships a default sweep; a real
  deployment tunes the window per feature to its own expected task duration.
- A task that legitimately runs long (an async job, a multi-step agent loop) is not "abandoned" —
  it is `pending` for as long as its resolution window allows. The window's job is to distinguish
  "still working" from "nobody is coming back to close this out."

## Correlating calls to an outcome

The same propagation mechanism as the attribution dimensions
([attribution.md](../attribution.md#attribution-must-be-captured-not-inferred)): whatever starts
the task generates `outcome_id` and puts it in the context every subsequent call in that task reads
it from, the same way `feature` and `tenant` propagate. A call made with no `outcome_id` in context
cannot be attributed to a task's outcome and is written with `outcome_id` set to an explicit
`unattributed` sentinel — visible and countable, never silently dropped, matching the cost-event
schema's rule for any missing required field.

## What this unlocks, precisely

With this contract, cost per outcome for a slice (a feature, a tenant, a route) is computable
exactly:

```
cost per outcome = SUM(computed_cost for every cost event whose outcome_id resolves to `succeeded`
                        in this slice, including every retried attempt of that task)
                    ÷
                    COUNT(distinct outcome_id with status = `succeeded` in this slice)
```

A retry storm shows up automatically: the retried attempts' `computed_cost` all land in the
numerator under the same `outcome_id`, while the denominator only grows when a task actually
succeeds — exactly the mechanism [cost-model.md](../cost-model.md) and the
[instrumentation diagram](../diagrams/instrumentation.md) describe, made concrete enough to
implement.
